# Internationalization (i18n)

## Scope for v1

Two languages: **English (default)** and **Bengali (বাংলা)**. Architecture must not hardcode "two languages" anywhere — adding a third later should mean adding one message file, not touching component code.

## Library & approach

`next-intl`, message files per locale:

```
lib/i18n/
├── en.json
└── bn.json
```

Locale is stored as a user preference in a small local settings table (Dexie) or `localStorage`, not in the URL path — this is a single-user local app, not a multi-tenant public site that needs SEO-indexable locale routes. Default locale on first launch: detect device language if it's `bn-*`, otherwise fall back to English; user can always override in Settings/hamburger menu regardless of detection.

## What gets translated

- All UI chrome: labels, buttons, headers, empty states, toasts, help text
- Relative time strings ("2 hours ago", "Today", "Yesterday") — use a locale-aware library (`Intl.RelativeTimeFormat` or `date-fns` with the `bn` locale) rather than hand-rolled strings
- Number formatting: **digits themselves stay Latin numerals (0-9) even in Bengali mode**, per common convention in Bengali fintech/commerce apps (Bengali digits ০-৯ exist but are far less commonly used for currency in everyday digital contexts than Latin numerals) — currency grouping still follows Indian convention (₹1,23,456) in both languages. This is a deliberate choice to double-check with the end user early, since it's a real judgment call, not a default to leave unquestioned.

## What does NOT get translated

- Person names, notebook names, notes — always user-entered free text, stored and shown exactly as typed, never machine-translated
- The app name "Khata" itself (already a Bengali/Hindi-origin word, recognizable in both languages)

## Layout implications (critical — covered in DESIGN-SYSTEM.md but restated here)

Bengali text runs meaningfully longer than English for the same meaning (commonly 20–40%). Every screen in SCREENS.md must be checked in both languages before considered done:
- No fixed-width buttons with English-length text budgets — buttons must accommodate the longer Bengali label without wrapping awkwardly or truncating
- The two-button Gave/Got row (the single most-used control in the app) is the highest-risk spot — Bengali equivalents ("দিলাম" / "নিলাম") are short, so this is likely fine, but must be visually verified, not assumed
- Bottom nav labels: keep to single short words in both languages (already reflected in the NAVIGATION.md table)

## Font pairing

Covered in DESIGN-SYSTEM.md: Inter (Latin) + Noto Sans Bengali, matched for x-height/weight so switching languages doesn't make the app look like two different products stitched together.

## Translation content ownership

Since the initial user (the brother) is a native Bengali speaker who will actually use this daily, Bengali strings should be reviewed by a native speaker before ship — not just machine-translated and left unchecked. This is explicitly called out because it's the one part of this spec a coding agent cannot verify on its own.
